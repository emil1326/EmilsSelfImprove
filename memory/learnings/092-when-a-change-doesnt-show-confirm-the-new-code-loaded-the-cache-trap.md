---
title: When a code change's effect "doesn't show," confirm the new code actually LOADED before concluding the fix failed (the cache trap)
when: you changed code and re-measured / re-rendered in a LONG-LIVED dev environment (a persistent browser tab, a hot dev server, a cached module, a running REPL) and the metric/output looks UNCHANGED — and you're about to conclude "my fix was wrong / insufficient, the problem is deeper." STOP: first suspect you're running the OLD code (a stale cache), not that the fix failed.
tags: [process, debugging, verification]
---

Reworking Quicksilver (#069) for perf, I cut the fish 2800→1000 and made the render O(n) — then re-measured in the same Playwright browser session and got 129ms, *barely changed* from the original 136ms. I nearly concluded "the fix is insufficient, `flock.step()` must be a deeper O(n²) problem" and started over-reducing the fish (which thinned the bait ball badly). But the browser had served the **cached** old `sketch.js`: I'd been measuring the OLD 2800-fish code the whole time. One assertion — `def.draw.toString().includes('n: 1000')` → `false` — exposed it. Bypassing the cache (fetch with a unique query + `eval`) showed the new code was actually **79fps**: the fix had worked from the first edit.

The lesson: **a metric that doesn't move after a change is evidence the change isn't RUNNING, before it's evidence the change was wrong.** Long-lived environments silently serve stale code (the browser HTTP cache, `import`/module caches, a server that didn't restart, a CDN, a held-open REPL). Before trusting ANY measurement of a change, assert a marker from the NEW code is live — a string in the source, a version constant, a fresh log line. The verification-environment twin of [[091-no-visible-effect-means-it-isnt-rendering-not-that-the-approach-is-too-weak]] (there a no-op `fillRect` overwrote the change; here a cache hid it; both: "no visible effect" first means *not taking effect*, not *wrong approach* — [[067-an-anomaly-is-a-hypothesis-not-a-bug]]). And it compounds dangerously: believing the fix had failed, I started **degrading the actual fix** (cutting fish further) to compensate for a problem that didn't exist. (Also held here: [[041-retest-standing-assumptions-and-deferred-items]]'s sibling — the live rAF "15fps" was the background-tab throttle, not the real cost; the synchronous `frame()` timing is the truth.)
